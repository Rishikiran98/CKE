# CKE: Research Viability — Retraction and Restatement

**This document replaces an earlier report that made empirical claims about CKE.
Those claims were not valid. This version states what was wrong, why, and what
is actually known.**

## 1. What the previous report claimed

The earlier revision of this file reported a benchmark comparison between CKE
and a dense RAG baseline on HotpotQA and 2WikiMultiHopQA. It claimed a large
multiple reduction in prompt tokens at comparable F1, gave subsystem maturity
scores out of ten for retrieval and conversational memory, and concluded that
the token-efficiency objective had been met. It drew those numbers from the
files under `results/`.

All of it is withdrawn. The figures are deliberately not restated here, so that
no reader or search finds them in this repository as though they still stood;
the original document is at commit `daa581d` for anyone who needs to check what
was claimed. The `results/` directory that held the underlying numbers has been
deleted, and `results/` is now ignored so that a benchmark run cannot quietly
restore it.

## 2. Why the results were invalid

Four independent defects each invalidate the comparison on their own.

**The corpus was generated by the repository to match its own extractor.**
`scripts/download_datasets.py` attempted a HuggingFace download and, on any
failure, silently fell back to `_make_synthetic(500)`. That function emitted
sentences in exactly the handful of grammatical forms the rule-based extractor
can parse, built from a fixed pool of 30 entity triples and 5 question
templates. Both `full_results_hotpotqa.json` and `full_results_wiki2.json`
contained the same 30 unique questions; the "2WikiMultiHopQA" file was the
HotpotQA synthetic set reshuffled under `random.seed(99)`. The gold answers were
also wrong on their own terms, for example pairing "What country is Stanford
University located in?" with the gold answer "California".

**No language model was in the answering loop.** Both the CKE arm and the RAG
arm were answered by `SimpleExtractiveQA` in `scripts/run_cke_benchmark.py`,
which returns the first 50 words of whichever retrieved sentence has the highest
token overlap with the question. This is why exact match was 0.0000 everywhere.
The reported F1 measures word overlap between a truncated sentence and a short
gold string; it is not a measure of either retrieval strategy.

**The token ratio was structural, not measured.** The RAG arm counted tokens
across ten concatenated documents. The CKE arm counted tokens across twelve
triples. The ratio between those two quantities is fixed by the units chosen,
and it would have been roughly the same whatever either system retrieved.

**The dense baseline was never dense.** Median RAG latency of 1.19 ms to embed
ten documents is not achievable with a sentence transformer on CPU, where 20 to
50 ms is typical. That latency is consistent only with
`EmbeddingModel._fallback_embed`, the 128-dimension SHA256 hashing path that
activates without warning when the model is unavailable. The baseline CKE was
compared against was a hash function.

Two further problems are worth recording. CKE's F1 was identically 0.1114 at
N=8, N=12, and N=20, so the retrieval-budget ablation varied a parameter that
changed nothing, which is a defect in path generation rather than a finding. And
CKE was roughly ten times slower than the baseline, 11.3 ms against 1.2 ms at
the median, a cost that appeared in the raw result files but in none of the
report's tables.

## 3. What is actually known about CKE

Only this:

- The codebase is organised into separable modules for extraction, graph
  storage, retrieval, reasoning, conversation, and trust calibration.
- The unit and regression suite passes; run `python -m pytest -q` for the
  current count. Those tests assert module-level behaviour. None of them
  establishes end-to-end answer quality.
- Nothing has been evaluated against an externally sourced dataset.

Accuracy, token cost, and latency relative to any baseline are all unknown. The
maturity scores in the previous report were not derived from measurement and are
not restated here.

## 4. What publication would require

The direction of the work is legitimate. Combining graph path retrieval with
symbolic operators and conversational memory is a reasonable thing to
investigate, and token cost against retrieval quality is a real trade-off worth
measuring.

Measuring it requires, at minimum:

1. Datasets from external, citable, checksummed sources. HotpotQA distractor
   dev, 2WikiMultiHopQA, MuSiQue, and LoCoMo for the conversational track. A
   loader that fails loudly when a dataset is absent, never one that substitutes
   generated data.
2. A real generator in the loop for every arm, with the same model, prompt, and
   decoding parameters across arms, so that the only variable is context
   content.
3. A dense baseline with a named embedding model at a pinned version and a real
   vector index, with the model identity recorded in the results metadata and
   the run aborting if the model fails to load.
4. Per-item records of exact match, F1, prompt and completion tokens,
   wall-clock latency, and retrieval recall against supporting facts, with
   latency reported in the same table as token counts.
5. Bootstrap confidence intervals on every headline metric, and a results file
   whose provenance is fully determined by its own metadata: commit SHA, dataset
   checksum, and model identifiers.

Until that instrument exists and has been run, CKE has no empirical story, and a
negative result from it would be a more useful contribution than the one this
document previously reported.
